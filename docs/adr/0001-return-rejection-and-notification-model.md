# ADR 0001：归还驳回分支 + 通知模型切分

- 状态：已接受
- 日期：2026-08-25
- 相关:契约 `.claude/contracts/return-rejection-and-notifications.md`;词表 `CONTEXT.md`(归还/逾期/通知章节)

## 背景

上线后使用中暴露两个问题:

1. **通知淹没**:自动提醒每天为每个逾期物品追加一条通知,一个逾期 10 天的物品会给借阅方留下 10 条"请归还";demo 账号已积累几十条,重要通知被埋。
2. **催错人 + 无驳回**:归还是单向三态机 `pending → requested → confirmed`,出借方在 `requested` 只有"确认收到"一个动作。若借阅方声明归还但实际没还,系统仍每天催**借阅方**"请归还"(他已声明还了),而真正卡住的出借方无从表达"我没收到"。

这三条原本是 v1 的有意决定(记录在 `CONTEXT.md`):
- 第 38 行:`requested → pending` 不允许(驳回分支推迟)。
- 第 93 行:`requested` 过期也算逾期(防借阅方钻空子)。
- 第 145 行:通知"追加而非合并"(简单、可追溯)。

## 决策

**一、归还机由单向改为带驳回回退。** 新增出借方"未收到"动作:`requested → pending`(`POST /items/:id/reject-return`),清 `returnedAt`、保留 `backDate`、通知借阅方(`return_rejected`)。防赖账机制从"死挂逾期标签"改为"出借方可驳回"。

**二、通知切分为「提醒」与「事件通知」两类。**
- **提醒**(`return_reminder`):对持续状态的反复催促,**收敛**为每 (item, 接收人) 一条(生成前先删同键旧提醒)。
- **事件通知**(`return_requested/confirmed/rejected`、`date_modified`):离散事实,**保持追加**。

**三、提醒接收人跟随瓶颈方**:`pending` 过期催借阅方归还,`requested` 过期催出借方确认。手动提醒仅 `pending` 可用。

**四、逾期语义拆两层**:逾期**标签**只给 `pending`(`requested` 不再显示逾期);提醒**触发**仍以 `backDate` 为界。

**五、通知留存 30 天**,午夜任务自动清理,不分读写。

## 权衡与备选

- **驳回 vs 维持单向 + 死挂逾期**:维持单向更简单,但把"防赖账"压在借阅方身上、且催错人。驳回让防赖账落到真正的相对方(出借方),更贴近现实,代价是多一条状态转移与一个动作。
- **提醒收敛 vs 追加**:追加最简单可追溯,但正是淹没的根源。收敛牺牲"提醒历史"(不保留"催了几次"),换取通知列表可用性——对提醒这种"状态镜像"类通知,历史价值低,取舍合理。事件通知仍追加,不受影响。
- **收敛用"先删后建" vs 加唯一约束**:唯一约束会误伤可重复的 `date_modified` 事件通知,故用应用层先删后建,无需 schema 变更。

## 已知取舍

- **跨状态的陈旧提醒不主动清理**:状态迁移(如 `pending → requested`)后,旧瓶颈方那条提醒不会在迁移时立即删除,依赖 30 天留存兜底自动消失。选择接受(而非在每次迁移时跨方清理),因其影响仅为短期一条陈旧提醒、有留存兜底,不值得为此在每个转移事务里加清理逻辑。
- **确认/驳回按钮无 in-flight 防抖**:快速双击时第二次请求会被 SQL 状态守卫挡下(数据无损),但前端可能弹一次 `invalid-state`。此为既有 confirm-return 同款模式,非本次引入,留待统一处理。

## 影响

- 推翻 `CONTEXT.md` 原第 38/93/145 行三条决定(已在本次同步更新)。
- 无数据库迁移(`return_rejected` 仅为 `Notification.type` 新字符串值;驳回复用现有字段;清理为查询)。
